Verifying that PARAM is working correctly

 

Because PARAM is a large, complicated program, there needs to be a relatively simple way of verifying that it's doing what it's supposed to do. 

Checking that older methods are correctly reproduced

Errors in heats of formation provide a good test of PARAM.  A standard reference for these errors is available on-line, this errors in individual species.  A limited amount of data is available on other methods, but only the results for PM7 and PM6 are complete enough to allow the verification of PARAM to be done.

To verify that PARAM correctly reproduces PM6 and PM7, follow these instructions:

Navigate to the sandbox folder in the Parameter Optimization folder, i.e., to the folder "%PARAM_Start%\Parameter Optimization\Sandbox"
Create a PARAM job with the name "Test PM6.dat" or "Test PM7.dat"
Edit this data set to include the following lines:
First line: " ref="../../reference data/Data normal" PMX" Replace PMX with either PM6 or PM7.
Next line: "end"
The next few lines should contain the reference file names of systems that are to be used in the test.  All the systems selected should exist in the on-line table and also exist in the local folder "%PARAM_Start%\Reference data\Data Normal". 

Here is an example of such a file:

 ref="../../reference data/Data normal" PM6
end
Silane 
Formaldehyde
Sulfur tetrachloride
As4O6
Iodine pentafluoride

Run the job using PARAM and compare the calculated errors with the values on-line. If they agree, then the conclusion can be made that PARAM gives the same results as MOPAC for existing methods.

Modified Methods

The reason that only PM6 and PM7 should be used in the previous test is that the modified methods, e.g. PM6-DH+ and PM6-D3H4, contain corrections designed to improve the accuracy of prediction of intermolecular energies. These corrections also change the heats of formation of individual species, and makes verification of PARAM more difficult.  If one of the modified methods is used for testing PARAM, it should only be used for calculating intermolecular interactions.

Checking that a normal PARAM job is running correctly

There is a simple test to show that PARAM is optimizing the parameters correctly.  The value of the SSQ (Sum of SQuares of errors) should drop as the parameterization proceeds.  To verify this, use a simple utility, "grep", included in PARAM, is ideal, to search for every line in an output file that contains the text "SSQ"  This test needs to be run at the command prompt level, so a command of the type:

   C:\Users\YourName\PARAM\Parameter Optimization\CHNOXSP\grep SSQ CHNOXSP.out

 should be used.

During a parameter optimization run a specific fault sometimes occurs in that a reference data chemical system will fail to give the correct results.  This can happen for any one of several reasons, with the most common being a failure to form a SCF.  When that happens, the results for that particular reference system would be nonsense, but will contribute to the SSQ, causing it to rise dramatically.  Failures of this type are detected by the difference between the predicted and calculated values, and the weighting factor(s) are adjusted to reduce the significance of the faulty results.  In practice, this can be seen by a sudden rise in the SSQ followed by an equally sudden decrease on the next cycle.  All isolated very large SSQ's of this type should be ignored.

The general behavior of the SSQ should be an initial rapid descent followed by a slowing as the minimum is approached.  For most parameterization runs, the job should be stopped when the rate of decrease in SSQ is too slow to justify further work.

That the results are internally consistent can be verified by using the optimized parameters from a PARAM job as input to a new PARAM job, using PARAM's EXTERNAL option, and checking that the resulting SSQ has the value expected. 

Finally, run MOPAC with one or more systems using MOPAC's EXTERNAL option and the optimized parameters from a PARAM job.  A good set of systems would be those used in checking that older methods are correctly reproduced.  For each system run using MOPAC, start with the ARC file and calculate the difference between the reference and calculated heats of formation.  These differences should be the same as those from the PARAM run and also the same as those from the verification run.   

During method development

Almost always during method development PARAM will start to produce unexpectedly bad results.  This is always due to user error.  When that happens, locate the last point at which the project was working as intended.  Then:

Look for mistakes.
Try splitting the next operation into parts, and move forward in smaller steps.
Check the first cycle of the output, looking for unexpected large errors.

Final points

The input parameter set used in checking that a normal PARAM job is running correctly must contain all the parameters used in that normal PARAM job. In particular, if parameters are supplied to the normal PARAM job, but are not optimized in that job, then those parameters must be read in to the verification jobs.  This situation occurs when only a limited set of parameters are optimized, for example, if, after the core parameters are optimized, parameters for sodium are optimized using the new core parameters as the starting point.  Then the new core parameters should be read in to any validation tests before the sodium parameters.
